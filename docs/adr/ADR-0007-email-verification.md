# ADR-0007: 이메일 확인은 플래그 하나로 하고, 복구는 막지 않는다

- 상태: 채택
- 날짜: 2026-10-14
- 관련: [ADR-0006](ADR-0006-account-recovery.md) 의 계정 복구, [ADR-0005](ADR-0005-smtp-without-library.md) 의 메일 발송

## 배경

ADR-0006 은 `User.Email` 을 확인하지 않기로 하고 확인 메일을 후속 과제로 남겼다.
그래서 지금은 사용자가 적은 주소를 그대로 믿는다.

- 오타를 내면 복구 메일이 남의 메일함으로 간다. 그 사람은 링크를 눌러
  남의 계정의 비밀번호를 바꿀 수 있다
- 남의 주소를 일부러 적어도 막히지 않는다

## 결정

### 1. `User.EmailVerifiedAt` 플래그 하나로 표시한다

```go
Email           string     `gorm:"index;size:256" json:"email" expr:"email"`
EmailVerifiedAt *time.Time `json:"emailVerifiedAt"`
```

주소는 지금처럼 `Email` 에 바로 들어가고, 확인한 시각만 따로 둔다.
`UpdateEmail` 은 주소가 달라지면 `EmailVerifiedAt` 을 `nil` 로 되돌린다.

**버린 선택지: `PendingEmail` 을 따로 둔다**

`Email` 에는 확인된 주소만 두고 확인 대기 중인 주소는 `PendingEmail` 에 담았다가
확인되면 옮기는 모양이다. 주소를 바꾸는 동안에도 이전 주소로 복구할 수 있다는 장점이 있다.

고르지 않았다. 필드가 하나 늘어나는 것보다 흐름이 둘로 갈라지는 쪽이 비싸다.
설정 화면은 "지금 저장된 주소" 와 "확인 기다리는 주소" 를 따로 보여줘야 하고,
`FindUserByEmail` 은 어느 쪽을 봐야 하는지 매번 정해야 한다.
그 대가로 얻는 것은 "주소를 바꾸는 중에도 이전 주소로 복구된다" 하나뿐인데,
아래 2 에서 미확인 주소로도 복구되게 두기로 했으므로 그 구멍 자체가 생기지 않는다.

### 2. 확인되지 않은 주소로도 복구는 된다

`RequestRecovery` 는 그대로다. 확인 여부를 보지 않는다.

확인된 주소만 복구에 쓰게 하면 위의 오타 문제는 깔끔하게 막힌다.
그러나 **이미 등록된 주소는 전부 미확인 상태로 시작**하므로, 그렇게 하는 순간
지금 복구할 수 있던 사람들이 한꺼번에 복구할 수 없게 된다.
마이그레이션에서 기존 행을 확인된 것으로 쳐 주는 방법도 있지만, 그러면
실제로 확인한 적 없는 주소가 영구히 "확인됨" 으로 남아 플래그의 뜻이 흐려진다.

대신 설정 화면에 확인 여부를 적는다. 사용자가 자기 오타를 알아볼 수 있는 자리를 만든다.

이것은 지금 데이터 때문에 내린 결정이고, 확인된 계정이 충분히 쌓이면 다시 볼 수 있다.
`docs/tasks.md` 에 후속 항목으로 남겼다.

### 3. 확인 메일은 설정 화면에서만, 저장할 때 자동으로 보낸다

`PATCH /api/v1/users/me` 가 주소를 저장한 뒤, 그 주소가 비어 있지 않고 아직 확인되지
않았으면 확인 메일을 보낸다. 같은 주소를 다시 저장하는 것이 곧 재발송이다.
따로 "확인 메일 보내기" 버튼을 두지 않았다. 누를 자리가 하나 줄고, 사용자가
저장 말고 할 일을 더 기억하지 않아도 된다.

**가입 폼(`POST /api/v1/users`)에서는 보내지 않는다.** 가입은 로그인 전이라
아무 주소나 적어 메일을 쏘는 통로가 된다. 가입 직후 설정 화면에서 보내면 된다.

**발급은 동기로, SMTP 만 백그라운드로 한다.** 복구 메일(`sendRecoveryMail`)은 bcrypt 까지
백그라운드로 민다. 계정이 있는 요청만 느려지면 존재 여부가 응답 시간으로 새기 때문이다.
확인 메일은 로그인한 사용자가 자기 주소에 보내는 것이라 샐 것이 없고, 대신
**보냈는지를 응답에 담아야 한다**. 재발송 간격(5분)에 걸리면 아무것도 나가지 않는데
화면이 "보냈습니다" 라고 적으면, 사용자는 오지 않는 메일을 기다린다.
그래서 `UpdateMeResponse.verificationMailSent` 로 알려주고 화면이 그대로 적는다.

SMTP 가 실패해도 저장은 되돌리지 않는다. 주소는 이미 바뀌었고 확인만 안 된 상태이며,
간격이 지난 뒤 다시 저장하면 재발송된다.

### 4. 확인 비밀은 `Verification` 테이블에 둔다

```go
type Verification struct {
	Username     string `gorm:"primaryKey;size:256"`
	Email        string `gorm:"size:256"`
	HashedSecret []byte
	ExpiredAt    time.Time
	CreatedAt    time.Time
}
```

`Recovery` 와 모양이 거의 같다. 그래도 합치지 않는다.

- 수명과 재발송 간격이 다르다. 복구는 15분/15분, 확인은 24시간/5분이다.
  복구는 로그인 못 하는 사람이 지금 당장 누르는 것이고, 확인 메일은 나중에
  메일함을 열었을 때 눌러도 된다. 확인은 로그인한 사용자만 보낼 수 있어
  재발송을 덜 조일 수 있다
- 한 테이블에 `purpose` 컬럼을 두고 섞으면, 복구 중에 이메일을 바꿨을 때
  두 비밀이 서로를 덮어쓴다. 사용자당 한 행이라는 구조가 그대로 버그가 된다

`Email` 을 같이 담는다. 발송이 백그라운드라 주소를 빠르게 두 번 바꾸면
먼저 걸린 발송이 뒤늦게 이전 주소로 행을 남길 수 있다. 확인할 때 지금 주소와
같은지 보고 다르면 거절한다.

**버린 선택지: HMAC 으로 서명한 stateless 토큰**

테이블이 늘지 않는다. 그러나 발급 기록이 없어 재발송 간격을 걸 자리가 없고,
이미 보낸 링크를 무효로 만들 수 없다. 주소를 바꿨을 때 이전 링크가 계속 살아 있다.

### 5. 확인 링크는 아무 세션도 열지 않는다

복구 링크(`EnterRecovery`)는 복구 세션을 열어 비밀번호를 바꾸게 해 준다.
확인 링크는 그러지 않는다. 메일함을 가졌다는 것은 그 주소가 닿는다는 증명일 뿐
로그인 수단이 아니다. 로그인도 요구하지 않아 다른 기기에서 열어도 된다.

이 브라우저가 마침 같은 계정으로 로그인해 있으면 세션에 든 `User` 만 갈아 끼운다.
그러지 않으면 설정 화면이 계속 "확인되지 않음" 을 보여준다.

## 결과

- 사용자는 설정 화면에서 자기 주소가 확인됐는지 볼 수 있다
- 오타를 낸 주소로도 여전히 복구 메일이 간다. 이 구멍은 그대로다.
  막으려면 2 를 뒤집어야 하고, 그때 기존 계정을 어떻게 할지 같이 정해야 한다
- passkey 로만 가입한 계정은 설정 화면에 들어가 주소를 적기 전까지 아무것도 달라지지 않는다
