# ADR-0004: gorm 기본 gob 직렬화기를 그대로 쓴다

- 상태: 채택
- 날짜: 2026-09-14
- 관련: [ADR-0002](ADR-0002-token-secret-per-kind.md) 의 "4. 직렬화는 gob 을 쓴다" 를 구체화한다

## 배경

다른 프로젝트(redzone-sector-0, ADR-0131)에서 gorm 의 `serializer:gob` 이 병목으로 나왔다.
같은 것이 여기에도 있는지 재보고 가져올지 정하기 위해 조사했다.

gorm 은 blob 마다 디코더를 새로 만든다.

```go
// gorm@v1.31.2/schema/serializer.go:176
decoder := gob.NewDecoder(bytes.NewBuffer(bytesValue))
err = decoder.Decode(fieldValue.Interface())
```

gob 은 스트림에 처음 나온 타입의 정의를 적고 Decoder 마다 그 정의로 디코드 엔진을 컴파일한다.
따라서 이 방식은 **행마다 타입 정의를 다시 적고 다시 컴파일한다.**
`encoding/gob` 문서가 전제하는 "하나의 Encoder 로 값을 흘려보내면 컴파일 값이 상각된다" 를 정면으로
깬다. Go issue #46089 에 같은 지적이 있고 고쳐지지 않은 채 닫혔다.

우리 쪽에서 살아 있는 태그는 세 곳이다. 실측한 값이다.

| 필드                           | blob 전체 | 값  | 타입 정의 |
|--------------------------------|-----------|-----|-----------|
| `auth.Token.Secret` (password) | 366B      | 68B | 298B      |
| `auth.Role.Rules`              | 179B      | 22B | 157B      |
| `auth.User.Labels`             | 32B       | 9B  | 23B       |

`Token.Secret` 디코드 1회 (Apple M4): **23.2µs · 10,864B · 252 alloc.**
타입 정의를 공유하면 **0.46µs · 253B · 6 alloc** 이다. 50배다.

## 결정

**그대로 둔다. 코드를 바꾸지 않는다.**

### 1. 이득이 들어갈 자리가 없다

redzone 에서 이것이 컸던 것은 한 라운드가 pawn·object·chunk 를 수백 행 읽고 그 합이 6.5ms 였기
때문이다. 여기는 그런 경로가 없다.

로그인 1회가 읽는 `token` 행은 1개다. 그 23µs 옆에 bcrypt 가 50~100ms 서 있다. 목록 조회
(`ListToken`, `ListUser`, `ListRole`)는 기본 limit 이 20 이다. 저장 크기도 같은 이유로 문제가
아니다 — redzone 이 17.25MB 에서 2.43MB 를 얻은 자리에서 여기는 수십 KB 다.

### 2. 후보를 재고 각각의 대가를 확인했다

`Token.Secret` 로 실측한 디코드 1회다.

| 방식                        | 시간   | 할당      | 저장 형식 | 스키마 변경 내성 |
|-----------------------------|--------|-----------|-----------|------------------|
| **지금 (`serializer:gob`)** | 23.2µs | 252 alloc | —         | 아래 표 A        |
| 갈라서 캐시                 | 0.5µs  | 6 alloc   | 그대로    | 아래 표 A        |
| 값만 저장 (redzone 방식)    | 0.46µs | 6 alloc   | 바뀜      | 아래 표 B        |
| 값만 저장 + preamble 테이블 | 0.46µs | 6 alloc   | 바뀜      | 표 A             |

- **값만 저장**: blob 에 값 바이트만 담고 타입 정의는 프로세스가 타입마다 하나씩 쥔다.
  크기까지 얻지만 스키마 변경 내성을 내준다(표 B). redzone 은 v1.0.0 전까지 세이브를
  버리기로 해서 받아들인 대가다. 여기서 그 행은 로그인 자격증명이고 `Secret` 은 최근 두 커밋에서
  계속 바뀌고 있는 타입이다.
- **갈라서 캐시**: 저장 형식을 그대로 두고 읽는 쪽만 바꾼다. blob 을 스캔해 타입 정의 구간과 값
  구간을 가르고, 정의를 키로 디코더를 캐시해 값 바이트만 먹인다. gob 스트림이 `[길이][메시지]`
  반복이고 메시지의 첫 값이 type id(음수면 정의, 양수면 값)라 경계를 찾을 수 있다. 가르는 비용은
  21ns 다. 마이그레이션도 롤백도 없고 스키마 변경 내성도 그대로다. 크기는 못 얻는다.
- **preamble 테이블**: 행에 값과 버전 태그만 넣고 옛 타입 정의를 별도 테이블에 보관한다.
  다 얻지만 구현과 운영 부담이 제일 크고 최초 전환 마이그레이션이 필요하다.

### 3. 안 하는 쪽의 대가는 코드를 안 들이는 것이다

"갈라서 캐시" 는 대가가 거의 없지만 공짜는 아니다. gob wire format 을 우리가 파싱하는 코드가
들어온다. 문서화된 형식이라 깨지면 에러가 나지 조용히 틀리지는 않지만, 23µs 를 아끼자고
표준 라이브러리의 바이트 형식에 기대는 코드를 심는 것이 지금 단계에서는 맞지 않는다.

### 4. 다시 볼 조건

- 목록 조회가 수천 행 규모가 되거나, 프로파일에서 gob 디코드가 보일 때
- 그때는 **"갈라서 캐시" 부터** 본다. 저장 형식이 안 바뀌어 되돌리기가 태그 원복으로 끝난다

## gob 의 스키마 변경 내성 (실측)

ADR-0002 의 "필드 추가는 안전하지만 타입 변경은 기존 행을 읽지 못하게 만든다" 를 실제로 재서
구체화한다. 옛 타입으로 `OAuth{Email, Name}` 한 행을 적어 두고 타입을 바꾼 뒤 읽었다.

| 타입 변경               | A: 행에 정의 있음 (지금)            | B: 행에 정의 없음 (값만 저장) |
|-------------------------|-------------------------------------|-------------------------------|
| 필드 추가               | 성공 (새 필드는 zero)               | 실패                          |
| 필드 삭제               | 성공 (없는 필드는 무시)             | 실패                          |
| 필드 이름 변경          | **성공하지만 값이 조용히 사라진다** | 실패                          |
| 필드 타입 변경          | 실패 (`wrong type`)                 | 실패                          |
| 중첩 구조체에 필드 추가 | 성공                                | 실패                          |

B 는 전부 `gob: unknown type id or corrupted data` 다.

가르는 것은 gob 이 **필드를 이름으로 맞춘다**는 점이다. 행에 "이 바이트는 `Secret{Password,
OAuth}` 다" 가 같이 들어 있으면 읽는 쪽에 `Passkey` 가 새로 생겼어도 이름이 맞는 것만 채우고
나머지는 zero 로 둔다. 행에 정의가 없으면 지금 타입의 정의로 옛 바이트를 해석해야 하는데, 필드가
하나만 늘어도 타입 번호가 밀려 이름을 맞춰볼 단계에 가지 못하고 깨진다.

**필드 이름 변경이 제일 위험하다.** 에러 없이 성공하고 값만 사라진다. 지금도 그런 것이라 새로
생기는 위험은 아니지만, 이름을 바꿀 때는 읽어서 옮기는 코드를 같이 넣어야 한다.

## 결과

- 코드 변경 없음. `serializer:gob` 태그 세 곳은 그대로다.
- 조사 중에 죽은 태그를 확인했다. gorm 에 넘어가지 않아 아무 일도 하지 않는다.
  - `auth.Rule` 의 `Verbs`, `Selector`, `Conditions` — `Rule` 은 `Role.Rules` 안에서 통째로
    직렬화되는 값이라 gorm 이 스키마로 보지 않는다
  - `pubsub.Event.Detail` — `pubsub` 은 gorm 을 import 하지 않는다
- 측정에 쓴 벤치와 스키마 변경 실험은 남기지 않았다. 위의 두 표가 그 결과다.
